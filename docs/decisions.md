## 2026-11-15 Data format of the M0 preprocessing

- **Decision**:
  1. **ID maps**: `customer_id` / `article_id` are sorted as strings and numbered 0..N-1, stored as int32 (`customer_idx` / `article_idx`). The numbering depends only on the set of IDs, not on the row order of the CSV. The customers are all customers of `customers.csv`, and the articles are all articles of `articles.csv`; an ID in the transaction table that is not in the map raises an error. `article_id` must be a string of 10 digits.
  2. **Dates**: the date of the transaction table is stored as the int16 column **`t_dat_day`** = `(t_dat − day_zero).days`, with `day_zero = 2018-09-20` written in the new `configs/preprocess.yaml`. Conversion between dates and day numbers is implemented **only** in `src/hmrec/data/day_index.py`, and every other module calls it. Preprocessing asserts that the earliest date equals `day_zero` and that the largest day number does not exceed the int16 limit.
  3. **Ordering and row groups of the transaction table**: `transactions.parquet` is sorted by `(t_dat_day, customer_idx)` (rows with the same key keep their original order, so the result is deterministic), with 1 million rows per row group (config item `transactions_row_group_size`) and min/max statistics, so that later date filters can skip row groups. It is verified that `t_dat_day` is non-decreasing. Fully identical duplicate rows are kept.
  4. **Cleaning of customers**: `postal_code` is dropped (no channel or feature uses it); `FN` / `Active` become int8 0/1 (null = 0); the `None` values of `fashion_news_frequency` (2 rows) are merged into `NONE`; other missing values of `club_member_status` / `fashion_news_frequency` stay null, and integer encoding is left to the feature layer. `age` is stored as int8 (null when missing).
  5. **Age buckets**: the column `age_bucket` is added following §5 R1; the bucket boundaries (inclusive at both ends) are written in `configs/preprocess.yaml`, and on load they are checked to be ordered, contiguous and non-overlapping.
  6. **articles**: `product_code` (int32) and the 6 category columns of §8.4 are kept; it is asserted that `product_code` equals the first 7 characters of `article_id`.
  7. **embedding**: the image / text embeddings are reordered by `article_idx` and stored in `data/processed/embeddings/` (float32 `[n_articles, dim]` + a bool mask); an article without an embedding is filled with 0 and has mask=False (the 0 is only a placeholder; the mask must be consulted when using it). **Every** row that has an embedding is checked to have an L2 norm within 1 ± 1e-3. The original embedding directories are not modified.
  8. **metadata.json**: at the end of preprocessing, `data/processed/metadata.json` is written (day_zero, the age buckets, the sha256 of the parsed values of `configs/preprocess.yaml`, the row counts of the tables). Downstream code that reads processed data checks it through `hmrec.data.metadata.scan_processed_parquet` / `check_processed_metadata` and raises an error if it does not match the current configuration.
- **Reason**: the type compression to int32 / int16 / int8 / float32 is a precondition of the memory plan in §1.3; sorting plus small row groups means less data is read when cutting a history at an anchor; the metadata check prevents old processed data from being used by mistake after `day_zero` or the age buckets change (which would shift every day number and break the time cut-off).

## 2026-11-16 Shared components: asof, the active pool, query_id, metric precision

- **Decision**:
  1. **Active pool configuration**: a new `configs/catalog.yaml` (`window_days: 28`, `min_purchase_lines: 3`), read by `hmrec.data.catalog` and shared by R1/R4/R5/R6. It is not put into `preprocess.yaml`: the active pool is computed on the spot for each anchor, does not affect the processed data, and should not change the config hash of the processed data. Under §2.4 these two values are frozen and are not hyperparameters; a change must be recorded in this file. Purchase records are counted by lines, and duplicate lines are counted separately.
  2. **query_id is globally unique**: `query_id = fold_ordinal × 10,000,000 + position` (int32). `fold_ordinal` follows the order of `fold_manifest.yaml` (D1 = 0 … T4 = 15), and `position` is the index within the fold in ascending `customer_idx`. The offset is written in the new `configs/queries.yaml`; it is asserted that the number of queries of every fold is below the offset and that `number of folds × offset − 1` does not exceed the int32 limit. A reverse function `decode_query_id` is provided. The queries and labels tables keep the `fold` column.
  3. **All date filtering is in `asof.py`**: both the history window and the label week. `label_week_transactions` may be called only by `data/queries.py`, enforced by `tests/unit/test_asof.py`, which scans `src/hmrec/` and `scripts/`. The window checks use `raise`, not `assert` (`python -O` removes asserts). AGENTS.md §3.1 has been updated accordingly.
  4. **Metrics use float64**: large arrays such as features, model inputs and embeddings still use float32; metric values and aggregated results use float64. AGENTS.md §4 states this exception. Metric results are fully reproducible: within a query, terms are summed in rank order; across queries, values are first sorted by `query_id` and then summed with `math.fsum` (exactly rounded, independent of order); after shuffling the input rows the results are bit-identical (tested).
  5. **Equality threshold of the selection**: two scores whose absolute difference is < 1e-12 are treated as equal, only to remove floating-point error; this does not change the meaning of "strictly better" in §4.2. `configs/selection_rule.yaml` is committed and cannot be modified, so this threshold is the commented constant `SCORE_EQUALITY_TOLERANCE` in `src/hmrec/hpo/selection.py`.
  6. **queries / labels are frozen once generated**: `scripts/m0_build_queries.py` does not overwrite existing files by default; an explicit `--overwrite` is required.
  7. **Thread setup extracted into `hmrec.threads`**: it depends only on the standard library and yaml, and scripts call `configure_polars_threads()` before importing polars; `m0_preprocess.py` was changed to use it as well.
- **Reason**:
  - When several folds are combined (the 4-week pooling of the D phase, the ranker trained on F1–F4), per-fold numbers would repeat, and a join on `query_id` alone would silently mismatch; globally unique numbers remove the problem at the root.
  - Filtering the label week is date filtering too, and only by placing it in `asof.py` is "date filtering happens in one place" guaranteed; but it reads the answers, so the callers are restricted by a test, not by documentation alone.
  - §4.2 requires "strictly better", and the rounding error of float32 (about 1e-7) could make equal scores look different; float64 plus a fixed summation order guarantees that the same input always gives the same score.

## 2026-11-16 D3 and D4 look like promotion weeks: the selection rule is not changed, a grouped diagnostic is added

- **Background**: measured queries of the 16 folds (`scripts/m0_build_queries.py`, independently checked by `scripts/checks/check_queries.py`): 69,000–120,000 queries per week, 82,000 on average; D3 (+46.9%) and D4 (+41.8%) are clearly larger, and their queries also have more labels each (4.0–4.1, against 3.1–3.6 in the other weeks), so they look like promotion weeks. In the query-weighted pooling of the D phase, D3 and D4 carry 236,182 / 391,681 = **60.3%** of the weight (the "about 54%" reported orally in an earlier conversation was a miscalculation; 60.3% is the correct value).
- **Decision**:
  1. **`configs/selection_rule.yaml` is not modified** (it was committed before any score was seen, and AGENTS.md §3.3 does not allow changing it either).
  2. In the D-phase report, besides the 4-week pooled score, the query-weighted scores of **D1–D2** and **D3–D4** are reported separately, **as a diagnostic only, not used for selection** (written into proposal §4.1).
  3. Proposal §12 gains known limitation 8 (D3 and D4 look like promotion weeks); the queries per week in §2.3 are changed to the measured values; the three rows candidate generation, ranker training and ranker inference in §1.3 are re-estimated with 82,000 queries per week and about 3.4 labels per query, with the calculation written out.
  4. Independent check scripts go into `scripts/checks/`. For the checks to mean something, they **do not use** `hmrec.data.asof`, `hmrec.data.queries` or `hmrec.data.day_index`, and derive the date windows again themselves with `datetime`. This is the only exception to the two AGENTS.md rules "date filtering only in asof.py" and "date conversion only through day_index.py"; it applies only to `scripts/checks/` and is noted in AGENTS.md §3.1.
- **Reason**:
  - The second condition of §4.2, "strictly better in at least 3 of the 4 weeks", **votes by week**: one vote per week, whatever the number of queries of that week. A configuration that is better only in D3 and D4 gets at most 2 votes and cannot pass; so although D3 and D4 carry 60% of the weight in the pooled score (the first condition), they cannot decide the outcome on their own. The rule itself already keeps a configuration that "only suits promotion weeks" from being selected, and there is no need to change it.
  - Conversely, the rule cannot tell us from which two weeks the gain of an accepted configuration mainly comes; the grouped diagnostic fills this gap and helps to interpret the D-phase results and the seasonality discussion of §6.7 / §12 items 1 and 2.

## 2026-11-16 Recall output spec; ordering of R1 fallback rows; the score of R2 recency-only

- **Decision**:
  1. **Each channel declares an output spec** (`OutputSpec`, `src/hmrec/recall/base.py`): the extra columns with their dtypes and the sort key are in one declaration. The default sort key is `score DESC, article_idx ASC`; a sort key must end with `article_idx ASC` (unique within a query, which makes the order unique). Extra column names must start with the channel's prefix (such as `pop_`) to avoid clashes when the wide table is merged; extra columns may not be null.
  2. **Two-way validation**: an undeclared extra column, a missing declared column, a dtype mismatch, null / NaN, a wrong `channel` value, a repeated article within a query, exceeding the quota, a `rank` that is not 1..n or does not agree with the declared sort key: each raises an error. Every kind of error has a unit test. All channels are ordered and numbered by the same `rank_candidates`; `score` is cast to float32 **before** sorting, so that the stored score and the order agree.
  3. **The ordering exception of R1**: the sort key is `pop_is_fallback ASC, score DESC, article_idx ASC`. Fallback rows use the global decayed score `S(i)` computed with the same τ as inside the buckets, and skip the articles already chosen in the bucket, so that nothing repeats within a query. The `score` of R1 (`pop_score`) therefore **mixes two scales**: bucket rows are `S(g, i)` and fallback rows are the global `S(i)`, told apart by `pop_is_fallback`; `pop_bucket_score` of group B gives every candidate the single scale `S(g, i)`. The number of fallback rows per fold and per age bucket is computed by `fallback_diagnostics` and written to the log (the HPO script of M2 also writes it to the result file).
  4. **R1 outputs only articles in the active pool A(a)**, and so does G0 (§2.4); this is a fixed rule in the code, not a config item.
  5. **The score of R2 recency-only = `1 / age_days`** (of the most recent purchase). Purchases on the same day score the same and are ordered only by `article_idx ASC`; information such as the number of purchases is not used to break ties. Every channel that computes `age_days = anchor_day − t_dat_day` asserts `age_days ≥ 1`; a 0 means data of the anchor day entered the history, and raises an error.
  6. **What R3 excludes**: only the very article the user bought within the 180-day style window; articles bought earlier are not excluded (in line with the definition in §5 R3). The market popularity `M(j)` uses the purchase lines of all users site-wide; an article not sold within the market window has `M(j) = 0`.
- **Reason**: the bucket score and the global score of R1 are on different scales, and forcing `score DESC` would put fallback rows before bucket rows, against the definition "bucket first, fill up only if short"; making the sort key part of the spec each channel declares is easier to check than a special branch for R1. The prefix on extra columns is there so that column names do not clash when §7.3 pivots the 6 channels into the wide table.

## 2026-11-16 R3 candidates outside the active pool: to be decided at M4 by a pre-registered criterion

- **Background**: measured on the full D1 (default configuration, quota 50), 679,893 of the 2,352,909 candidate rows of R3 (**28.9%**) are outside the active pool `A(a)`. They hit only 88 times, a hit rate of **0.013%**; the hit rate of the candidates inside `A(a)` is **0.48%** (about 37 times higher). The candidates outside `A(a)` make up only **1.1%** of R3's hits.
- **Decision**:
  1. R3 is not changed now (§2.4 still says R2 and R3 are not filtered by the active pool).
  2. In the union check of M4 (proposal §5.7 item 4), on D1–D4, measure the share of R3 candidates outside `A(a)`, their hit rate, and the change in union recall when those of them "not recalled by any other channel" are removed.
  3. **Pre-registered criterion**: if union recall drops by **< 0.1 percentage points** (absolute) → R3 is changed to output only articles inside `A(a)`; otherwise it stays as it is.
  4. The same statistics are computed for R2, as a diagnostic only, with no change.
- **Reason**: the D-phase configuration of R3 is selected by Recall@50. Removing the candidates outside `A(a)` hardly affects R3's own recall, but the benefit of fewer useless rows (the number of merged candidates, and the rows of feature computation and ranker inference) does not show in Recall@50, so it does not fit as an R3 ablation and is made a system-level decision at M4.
- **Stated candidly**: this criterion was set **after seeing the D1 results**; it was not registered beforehand. To limit the effect of this, the threshold was fixed before the results of D2–D4 and of union recall were seen, and is not changed afterwards.

## 2026-11-17 R4 ItemCF: the active-pool filter comes before Top-K_n; implementation of chunking and of several α

- **Decision**:
  1. **The neighbours `j` of R4 are restricted to `A(a)`, and the filter comes before taking the Top-`K_n`** (the original text of proposal §5 R4 only said "the output is limited to `A(a)`" and did not say where the filter goes). `C_w`, `n_w` and `d_u` are computed from all articles of the fit window and are not affected by `A(a)`; seeds are not required to be active. Tests guarantee: filtering first and then taking the Top-`K_n` gives exactly the same result as "computing the full seed × all-articles similarity matrix, dropping the inactive articles, then taking the Top-`K_n`"; changing `A(a)` does not change `C_w` and `n_w`; inactive seeds still contribute to the score.
  2. **Chunking and several α**: `C_w` is not stored as a whole; it is computed in chunks of seeds (`chunking.item_chunk_size`) by scipy sparse matrix multiplication, and for each chunk the Top-`K_n` is taken once per α before the chunk is released. So several α of the same week and the same variant share one computation of `C_w` / `n_w` without `C_w` being stored (on D1, `Σ d_u²` ≈ 510 million (i, j) combinations, which would not fit in memory as a whole). scipy is used rather than a Polars join + group_by: in the sparse product every element of `C_w` is summed in a fixed order of users, so the chunked and the unchunked results are bit-identical; the floating-point summation order of a multi-threaded Polars group_by is not fixed.
  3. **Only the seeds used by this week's queries are computed** (D1: 28,110); the output is the same as computing all articles and looking them up.
  4. **CF0 / CF3 decide only the user weights** (1 or IUF); α is a separate config item; the CF0 ablation uses α=0.5.
- **Reason**:
  - The graph of the D1 fit window has 71,713 articles, of which only 20,764 (29%) are in `A(a)`. Estimated by article counts, about 71% of the neighbour slots could fall on inactive articles; **measured**, when the Top-100 is taken first and filtered afterwards, **45.4%** of the neighbour slots are inactive articles (D1, CF3, α=0.7; popular articles are mostly active, hence below 71%). With the filter before the Top-`K_n`, each seed keeps 99.05 active neighbours on average.

## 2026-11-17 Seed window and seed decay added to R4 (a 3×2 grid, added before the D-phase HPO started)

- **Decision**:
  1. The user score of R4 becomes `S(u, j) = Σ_i q_ui · s(i→j)`. With seed decay on, `q_ui = exp(−age_ui / τ_seed)`, where `age_ui` is the number of days since the user's most recent purchase of seed `i`, and `τ_seed` is fixed at 30 (as for R2 and R3) and not tuned; with it off, `q_ui = 1`. Building the graph (`C_w`, `n_w`, `d_u`) involves no decay.
  2. After CF0/CF3 and α, the HPO of R4 gains a 3×2 grid: `L_seed ∈ {90, 180, 365}` × seed decay {off, on}, with (90, off) as the default configuration. R4 goes from 4 configurations to **9** in total (proposal §5 R4 and §5.8 updated).
  3. This step does not follow "one factor at a time" and uses a grid: the longer the window, the more noise old purchases add without decay, so the two factors clearly interact; each configuration takes only a dozen seconds or so.
  4. The CF0 ablation uses α = 0.5 (plain cosine).
  5. The result of the default configuration (90 days, decay off) is exactly the same as before (tested).
- **Reason**: measured on D1, **32.2%** of the queries of R4 (25,201 / 78,193) get an empty output because they have no purchase within 90 days. A longer seed window can cover these users, but decay is needed to control the noise of old purchases.
- **Timing**: these configurations were added **after seeing the result of R4's default configuration on D1 and before the D-phase HPO started**. Only the D1 result of the default configuration was seen (Recall@100 and the share of empty queries); no score of any new configuration had been seen.

- **Decision**:

## 2026-11-17 Selection rule with several candidates; chunked scoring for R5; vectors.py added to the layering diagram of AGENTS.md

- **Decision**:
  1. **When a step has several candidates** (a new paragraph in proposal §4.2, implemented in `src/hmrec/hpo/selection.py`; `configs/selection_rule.yaml` is not changed): each candidate is compared with the current default under the two conditions of §4.2; if no candidate passes, the default is kept; if some pass, the passing candidates whose relative gap to the highest pooled score is < 1% count as "about the same", and the one that comes first in the priority order is chosen. If the highest-scoring candidate does not pass and another one does, the passing one is chosen.
  2. **The priority order** is written in `configs/hpo/d_phase.yaml`, committed before the run and not changed after it: where candidates differ in simplicity / cost, the listed order applies (simpler / cheaper / closer to the default first); purely numeric parameters (τ, γ, α, λ, α_conf) are ordered by distance from the current default, the smaller value first at equal distance. R4 seed grid: (90, off) [default] < (90, on) < (180, off) < (180, on) < (365, off) < (365, on).
  3. **The iterations of R5 are a convergence check** and do not use the multi-candidate rule: it changes to 25 only if 25 passes §4.2 against 15; if 25 is clearly worse than 15 (the pooled score drops by ≥ 1% and at least 3 weeks are strictly worse), or if 10 passes §4.2 against 15, nothing is selected automatically, and the run stops for a person to decide whether to go back to the λ step.

## 2026-11-17 Definition of the Two-Tower training samples and user history (M3 step 7)

- **Decision**:
  1. **Positive samples**: one per (customer_idx, purchase date, article_idx). A user buying the same article several times on the same day (several identical purchase lines) counts as one positive sample. The original text of proposal §6.1 was "one positive sample per purchase"; it is now deduplicated by day.
  2. **Groups**: all positive samples of the same user on the same day share one `group_id` (samples are sorted by (t_dat_day, customer_idx, article_idx), so the rows of a group are contiguous), which lets the multi-positive loss of §5 R6 recognize samples that "are positives of each other and may not serve as negatives".
  3. **User history**: the 20 most recent purchases **before** the purchase date (`t_dat_day` < purchase date, the day itself excluded), with no time window (back to the first day of the data). Purchases in the history are deduplicated **in the same way** as positive samples (the same article on the same day counts once); the same article bought on different days counts several times. Order: most recent first; several items on the same day in ascending `article_idx`, so the result does not depend on the row order of the file. Histories shorter than 20 are padded at the end, with `history_mask = False`. **The padding index is `n_articles`** (real articles are 0..n_articles−1, so the padding corresponds to no real article; if the mask is ever forgotten somewhere, no real article is silently mixed into a user's history).
  4. **A padding row is added at the end of the item feature table** (index `n_articles`): image and text vectors all 0, both masks False, product_code and category codes all 0. The table has `n_articles + 1` rows. The article-ID embedding of the model uses `padding_idx = n_articles`; the category embeddings use `padding_idx = 0` (in the item table only the padding row has code 0; these columns have no nulls for real articles).
  5. **Profile and category encoding**: age_bucket, club_member_status, fashion_news_frequency, as well as product_code and the 6 category columns of §8.4, are all encoded as integers: 0 = null, 1..K = the deduplicated values in sorted order.
  6. **Storage**: the sample arrays (`customer_idx`, `t_dat_day`, `article_idx`, `group_id` [N], `history` int32 [N, 20], `history_mask` bool [N, 20]) are stored as `.npy` under `artifacts/twotower/data/{window name}/`, never overwriting an existing directory. The base window is written in `configs/twotower.yaml`: purchase dates [2020-06-03 − 182 days, 2020-06-03), i.e. 2019-12-03 – 2020-06-02.
- **Reason**:
  - Duplicate purchase lines on the same day are usually several pieces bought in one go and carry no extra information about "what is bought next"; with deduplication by day, positive samples and histories count in the same way, and one article does not take several slots of a history.
  - Item 3, "the history is deduplicated by day too", was proposed by the agent during implementation and confirmed by the user before the commit.
  - Padding first used `article_idx = 0`; 0 is a real article, and a forgotten mask would fail silently, so before the commit it was changed to `n_articles` at the user's request, and the padding row was added to the item feature table.
- **Proposal §6.1 has been updated.**

## 2026-11-17 Two-Tower model structure, loss, training settings and the selection of E_base (M3 step 8)

The full structure and all fixed values are in proposal §5 R6 and `configs/recall/r6_twotower.yaml`. Below are the decisions that are new or more specific than the original text of the proposal; all were made **before any R6 score was seen**.

- **Decisions and reasons**:
  1. **The parts of the item tower are concatenated, not summed**: image 128, text 128, article ID 64, product_code 32, the 6 category fields 90 (by the rule of the next item), 442 dimensions in total. Reason: summing requires every field to be 128-dimensional, so fields with very few values would also take 128 dimensions; with concatenation each field gets a suitable dimension, and the following layers decide how to combine them.
  2. **Encoding rule for categorical features** (for both towers): a field with ≤ 20 values (including the missing code 0) is one-hot; one with > 20 values uses a 16-dimensional embedding (`padding_idx = 0`, initialized N(0, 0.02²)); article ID (64 dimensions, `padding_idx = n_articles`) and product_code (32 dimensions) are exceptions and are both initialized to 0. On the actual data: product_group_name (20), index_group_no (6), age_bucket (8), club_member_status (4) and fashion_news_frequency (4) are one-hot; product_type_no (133), garment_group_no (22), section_no (58) and colour_group_code (51) use embeddings. Reason: for a field with very few values, an embedding dimension above the number of values is pointless; the following Linear would merge the surplus dimensions, adding only parameters and noise. IDs are initialized to 0: for an article not seen in training this part stays 0 and adds no random noise.
  3. **Both towers get one non-linear layer**: after concatenation → `Linear(→ 256)` → ReLU → `Linear(256 → 128)` → L2 normalization. Reason: with only a linear combination after concatenation, interactions between fields cannot be expressed (for example, the image matters differently in different categories).
  4. **Position-weighted pooling**: each of the 20 history positions learns one scalar weight, with a softmax only over positions that hold a purchase (all weights start at 0, i.e. it starts as a masked mean); with an empty history, pooled = 0. Reason: the history is ordered from most recent to oldest; adding seed time decay to R4 improved it by 14.5%, which shows recency matters, while a masked mean treats all positions alike.
  5. **Duplicate-aware** (**not in the original proposal; this is a new requirement**): the columns of the loss are the deduplicated target articles of the batch, and an article that appears several times is one column. Reason: popular articles are often bought by several users in the same batch; without deduplication they would count as several negatives for the other users, and the penalty would be counted repeatedly. The columns of the other positives of the same group are set to −∞ (multi-positive, already in the original proposal). τ = 0.05; the `Q(k)` of LogQ is computed from the current training set only (base: all base training samples, excluding the alarm users; fine-tune: the new week + replay of that run).
  6. **Device selection rule**: the real model runs 200 steps each on mps and on cpu (one process each, the first 10 steps not timed); MPS is used only if its mean time per step is **more than 1.3 times** faster than CPU, otherwise CPU. Reason: the backward pass of embeddings on MPS is not deterministic, so the training result cannot be reproduced exactly; on CPU the result is bit-reproducible (tested). `training.device` in `configs/recall/r6_twotower.yaml` is written as `cpu` for now and settled by this rule after the benchmark, with the result recorded in a separate entry.
  7. **How E_base is selected** (proposal §6.3 only said "by the rule of §4"): default epoch 1, candidates epoch 2–6, fewer epochs first (less training = cheaper), selected by the multi-candidate rule of §4.2, written in `r6_twotower.base_epoch` of `configs/hpo/d_phase.yaml`. If epoch 6 (the last checkpoint) is selected, the run stops for a person to decide (`stop_at_boundary`).
  8. **Training settings**: Adam (β = 0.9, 0.999, ε = 1e-8), lr 1e-3 fixed with no decay (fine-tune 1e-4), weight decay 0 (the output is L2-normalized, so the size of the weights does not affect the scores, and decay would only shrink the ID rows of rare articles), no gradient clipping; batch 512, a shuffled order generated on CPU from `(seed, epoch)` for every epoch, the last incomplete batch kept; 6 epochs; seed 42; 1% of the users held out as an alarm, for which only the loss is recorded.
  9. **Implementation**: R5's "take the Top-quota by vector dot product, recompute the score with `dot_pairs`" moves to `src/hmrec/recall/vector_scoring.py`, shared by R5 and R6 (the results of R5 do not change, and all R5 tests pass); `make_trial_id` and the JSON serialization of `results/d_phase.csv` gain `default=str` (the R6 config contains dates; the trial_ids of R1–R5 do not change).

## 2026-11-17 Definition of the Two-Tower training chain (§6.4): replay, Adam, the default configuration and the order of candidates

- **Timing**: the definitions below were fixed **after seeing the E_base result (epoch 4 selected, 4-week pooled Recall@100 11.84%) and before any training chain was run**. No fine-tuning score had been seen.
- **Decision**:
  1. **Training chain**: starting from epoch 4 of the base, in the order D1 → D2 → D3 → D4, each week the current model first predicts (and is scored), then is fine-tuned on the data of that week (purchase dates `[a, a + 7)`); after predicting D4 it is also fine-tuned once, giving M4 (used for F1). The model of every step is saved to `artifacts/models/twotower/chain/{trial_id}/{fold}.pt`, never overwriting.
  2. **Meaning of replay = 50%**: samples are drawn without replacement from the 4 weeks before the week begins (`[a − 28, a)`), as many as the new data (new : old = 1 : 1); the general formula is `n_replay = round(n_new × replay / (1 − replay))`; with replay = 0 only the new data are used. Sampling uses a fixed seed.
  3. **Alarm users**: the 1% of users held out in base training remain excluded (the same users are drawn again from the base arrays and the base seed), and their loss is recorded every week.
  4. **Adam is re-initialized every week** (lr 1e-4, otherwise as for the base), without inheriting the optimizer state of the previous week. Reason: each week's data and LogQ distribution differ, and the momentum and second moments of the previous week no longer match the current gradients; starting each week from the same initial state also keeps the weekly settings identical and easy to reproduce.
  5. **The Q of LogQ** is computed from the fine-tuning set of that run (new data + replay).
  6. **The default configuration is frozen** (no update; the result of E_base epoch 4 is reused directly). So that this trial is reused, `hmrec.hpo.runner.parsed_config` specifies: when `e_update = 0`, the settings `replay`, `chain_seed` and `chain` do not affect the result and do not count towards the trial_id, so the 6 trial_ids of E_base stay unchanged (tested).
  7. **Candidates and priority order**: (E_update = 1, replay = 0) < (1, 50%) < (2, 0) < (2, 50%), selected by the multi-candidate rule of §4.2 (fewer epochs and no replay are cheaper and come first). All configurations score the same on D1, so "strictly better in at least 3 of the 4 weeks" in effect requires D2, D3 and D4 all to be better, which is intended.
  8. **Robustness**: the top 2 configurations by the rule (the 2nd = the one the rule would select if the 1st were removed; ordered by pooled score if no candidate passes) are each run again with seeds 43 and 44, which affect only the shuffling order of fine-tuning and the replay sampling; the mean, standard deviation, minimum and maximum are reported. The selection is still based on the result of seed 42; the extra seeds are for reporting only. Written in the new `robustness` section of `configs/hpo/d_phase.yaml`.
  9. **Memory**: the chain processes one fold at a time, and each week's fine-tuning arrays are released after the week; the fine-tuning history reads only the purchases of the users involved (as in inference). Each stage of prediction (history, vectors, candidates) records its memory, to find the cause of the 6.27 GB peak of the first trial in the E_base evaluation (results recorded separately after the run).

## 2026-11-17 True memory peak recorded by memory.py (ru_maxrss); where the 4.78 GB comes from

- **Where the 4.78 GB comes from**: the **4.78 GB** in the two entries above ("Results after changing R3 to output only A(a)", "M5: all recall configurations locked") and in proposal §1.3 comes from the **terminal output** of `/usr/bin/time -l` and **was not written to the run log** (`artifacts/runs/m4_union_check_r3_active_pool/run.log` has only sampled values, at most 4.72 GB). - **Decision**: from now on the true peak is recorded by `src/hmrec/memory.py` itself and no longer depends on terminal output.
  1. New `read_process_peak_memory` / `log_process_peak_memory`: they read the true maximum RSS since the process started with the standard library's `resource.getrusage(RUSAGE_SELF).ru_maxrss` (the same counter as `/usr/bin/time -l`); the unit is handled by `ru_maxrss_to_bytes` (bytes on macOS, KB on Linux). `RUSAGE_CHILDREN` is read as well (the largest finished child process, not the sum) and is written to the log only when a child process has finished.

Whether 6 GB is exceeded is judged by the true peak.
  3. Every `MemoryTracker` writes both numbers to the log when it ends; a script calls `log_process_peak_memory` as its last step (logging a WARNING when `memory.limit_gb` is exceeded) and writes the true peak into the result record of the run.
  4. Every run of the M5 lock check appends one row to the new file `results/m5_lock_check.csv`: the two scores, whether they are bit-identical, the run time, `sampled_peak_rss_gb`, `process_max_rss_gb`, `children_max_rss_gb`, the git commit. A run whose scores differ is recorded as usual and only then raises an error.

The scripts of M0–M4 did not get the "last step" call; they obtain the true peak in the log through their own `MemoryTracker`. Scripts and result records written from M6 on follow item 3.

## 2026-11-18 Two things found while implementing M7: torch and LightGBM cannot share a process; a timing-only training does not need a tree count that is a multiple of 100

- **OpenMP conflict between torch and LightGBM**
  - **Symptoms**: after the tests were written, the integration test segfaulted while LightGBM built a Dataset, and the full `make test-fast` hung without ending (stopped by hand after waiting 10 minutes); importing torch and then lightgbm in plain python and then training made the process exit at once with `OMP: Error #15: Initializing libomp.dylib, but found libomp.dylib already initialized`.
  - **Cause** (confirmed with `DYLD_PRINT_LIBRARIES`): torch loads its own `.venv/.../torch/lib/libomp.dylib`, and LightGBM loads Homebrew's `/opt/homebrew/Cellar/libomp/22.1.4/lib/libomp.dylib`, so one process holds two copies of the OpenMP runtime. It had not surfaced before because M0–M6 did not use LightGBM.
  - **What was done**:
    1. M7 processes do not load torch. `git_state` and `warn_uncommitted_changes` move from `hpo/runner.py` (which imports `recall/` and through it torch) to the new bottom-layer module `src/hmrec/git_state.py`; `hpo/runner.py` still re-exports the two functions, so the scripts of M2–M6 and `tests/unit/test_hpo_runner.py` need no change; the name in the logs stays `hmrec.hpo.runner`. `tests/unit/test_m7_code_rules.py` imports the modules M7 uses in a fresh process and confirms that neither torch, nor implicit, nor `hmrec.recall` has been loaded.
    2. Tests run in two processes: `uv run pytest tests/unit` runs only the torch side, and `--lightgbm-side` only the LightGBM side (file names starting with `test_ranker_`, `test_v_`, `test_speed_test`, `test_m7_`); the files of the other side are not imported. `make test-fast` and `make test` run both. When torch and lightgbm both appear in one test process, `tests/conftest.py` fails the run.
    3. AGENTS.md §5, §7 and §8 state these two rules (the `fusion/` rule of §5 was requested by the user; `git_state.py`, "may not import torch", and "tests run in two processes" of §7 were added this time to solve this problem).
  - **A fact about the environment**: the OpenMP runtime of LightGBM comes from Homebrew (libomp 22.1.4) and is not in `uv.lock`, so its version is not locked with the repository.
  - **libomp is a system dependency outside `uv.lock`; after upgrading it, the check "two trainings give the same model" has to be done again** (train twice with the same binary Dataset and the same parameters, and the model text must be the same; and the first k trees of a model trained to more trees must equal a model trained to k trees); only after the check passes may new results be produced. The installation steps of the README state `brew install libomp` and the current version 22.1.4.
  - **Every M7 process records the libraries it actually uses** (`src/hmrec/ranker/runtime.py`): `results/v_phase.csv`, `results/m7_speed_test.csv` (one row per trial) and `results/m7_runs.csv` (one row each for sampling, building a Dataset, the RRF baseline) all have the three columns `lightgbm_version`, `libomp_path`, `libomp_version`. The path comes from the operating system's "libraries loaded in this process" (the dyld list on macOS), not from a guess by install location; the version is read from the Homebrew path `.../Cellar/libomp/<version>/...`, and other locations are recorded as `unknown`. The two driver scripts (`m7_speed_test.py`, `m7_ranker_hpo.py`) write no result rows themselves and only write these three items to the run log. If two copies of the OpenMP runtime are loaded in a process, `read_lightgbm_runtime` raises an error; every M7 script calls it at start-up.
- **A timing-only training does not need a tree count that is a multiple of the checkpoint interval**: the first version of the check required the number of trees of every trial to be a multiple of `checkpoint_every` (100), but the trainings of the speed test that compare the two histogram modes have 50 trees and would be rejected by this check. The small-data integration test found the problem (before anything ran on the full data). Now only trials that are evaluated need a number of trees that falls on a checkpoint.
- **Not done yet**: `histogram.mode` in `configs/ranker.yaml` is still `undecided`; no step of M7 has been run on the full data yet; `configs/locks/ranker.lock.yaml` is written only after V4 is finished.

## 2026-11-18 The definition of NDCG@K spelled out (the independent check script found the wording of the proposal ambiguous; the code and the recorded values are unchanged)

- **How it was found**: before the grid of step 1, the independent check script (`scripts/checks/check_ranker_eval.py`, plain loops) recomputed the V1 metrics at 100, 200 and 300 trees from the Top-12 saved by the speed test. MAP@12 and Recall@12 agree with the records (differences below 1e-9), **NDCG@12 does not**: recomputed 0.044708 / 0.045780 / 0.046338, recorded 0.044900 / 0.045978 / 0.046538. The rank checks (no more than 12 rows per query, consecutive ranks, ordered by score DESC, article_idx ASC) pass. Under the stop conditions, the RRF baseline and the grid were not run at that point.
- **Cause**: proposal §2.5 used to say "the ideal DCG is computed from the complete `G_q`", which is ambiguous. The check script read it literally as "the ideal ranking has `|G_q|` hits, not cut off at K"; `src/hmrec/eval/metrics.py` (written in M1 and in use ever since) implements "the ideal ranking has `min(K, |G_q|)` hits". The two differ only for queries with more than K labels: V1 has 1,859 queries with more than 12 labels (2.2%, at most 65 labels), and overall the difference is about 0.43%.
- **Decision (user)**: the definition of `eval/metrics.py` is kept: the number of hits of the ideal DCG is `min(K, |G_q|)`. The sentence meant "the ideal ranking uses all the labels the user actually bought, not only the recalled part"; the cut-off is implied by @K.
- **What changed**: proposal §2.5 now spells out NDCG@K (DCG looks only at the first K positions; the number of hits of the ideal DCG is `min(K, |G_q|)`; `G_q` is everything actually bought in the label week, not only the recalled part; a perfect ranking scores 1.0); the ideal DCG of the check script was changed to the same definition, and a hand-computed test with more than 12 labels was added.
- **What did not change**: `eval/metrics.py` and its tests were not changed; every NDCG in the earlier records (`results/d_phase.csv`, `results/m4_*.csv`, `results/m7_speed_test_metrics.csv`) uses this definition, and the values stand. **Selection metrics are not affected**: the recall channels use Recall@K and the ranker uses MAP@12; NDCG has only ever been a reported item.
- **While at it, the other definitions of §2.5 were compared item by item with `eval/metrics.py`**; no inconsistency was found; four points that had not been written out were added to §2.5 this time:
  1. The denominator of Recall@K is the complete `|G_q|`, not cut off at K (unlike AP and NDCG), so for a query with more than K labels Recall@K is at most `K / |G_q|`.
  2. AP@K used to state only the denominator `min(12, |G_q|)` and not the numerator; `Σ P(r)` (summed over the hit positions among the first K) was added.
  3. `G_q` of all three metrics is everything actually bought; a query with no prediction or no hit scores 0 and stays in the denominator (already in §2.3, restated here).
  4. The position is determined by `rank`; `rank` must be 1, 2, …, n, with no repeated article within a query; a query in the predictions that is not in the label table is an error (the code has always checked this).

## 2026-11-19 Stage 2 (M9): DeepFM as an alternative ranker; the controlled comparison and the rules of the study (recorded before any DeepFM result exists)

- **Decision** (by the user): a DeepFM ranker is implemented next to the locked LightGBM ranker, to understand the difference between a pointwise deep model and a listwise GBDT on the same inputs. **Replacing LightGBM is not the goal.** The locked system, the lock files, the existing results and the existing artifacts are not changed. Branch `m9-deepfm`.
- **Controlled comparison (fixed)**: the same candidates; the same 71 locked features (the wide tables are verified before they are read); the same 4-week training window; the same training rows as LightGBM (the M7 sample files with ratio 40, used only after their sha256 is checked against their own record and against the record of the LightGBM Dataset of the same target week); target weeks V1–V4 only; main metric MAP@12 on the Top-12 with the existing evaluation code. The DeepFM code refuses T folds.
- **Default model** (proposal §16.2): one field per feature; the 8 categorical features with their codes; the 63 numeric features in 32 quantile bins plus a bin for missing values, with edges from the training rows of each window only; embedding dimension 16 shared by the FM part and the deep part; FM part = first order + second order between all fields; deep part = MLP 256 → 128 → 64 → 1 with ReLU; output = FM logit + deep logit; pointwise binary cross-entropy; Adam, learning rate 1e-3, batch 4,096, no weight decay, dropout 0, 5 epochs with a checkpoint after every epoch, seed 42.
- **Variants** (proposal §16.3; implemented and tested now, run later): components (first order only; FM; deep only; full); numeric input without binning (standardised and clipped at the 0.1st / 99.9th training percentiles, with a separate indicator for missing values); listwise softmax cross-entropy per query with batches of whole queries.
- **Rules of the study, set before any result** (proposal §16.5, `configs/hpo/deepfm.yaml`):
  1. Epoch rule: for each configuration, the smallest epoch whose pooled MAP@12 is within 1% of its best (the same rule as for the number of trees).
  2. Step 0, noise: the default configuration with seeds 42, 43, 44; if the range of the pooled MAP@12 across the seeds is above 1%, stop and report before any tuning.
  3. Tuning one factor at a time with the existing selection rule (at least 1% relative gain and strictly better in at least 3 of 4 weeks): learning rate {3e-4, 1e-3, 3e-3}, then embedding dimension {8, 16, 32}, then dropout {0, 0.1, 0.3}; the value closer to the default first, the smaller first at equal distance; selection with seed 42.
  4. Ablations at the selected configuration without separate tuning: the four component variants, the numeric-input variant, the listwise-loss variant.
  5. Final report: 3 seeds for the selected configuration, and a 95% interval of DeepFM minus LightGBM on V with the existing customer-level bootstrap.
  6. One evaluation on T1–T4 after the configuration is locked on V: run once, reported only, never used to select anything. **The user consents to this read of the T labels** (AGENTS.md §3.2); it will be recorded when it happens. It is not implemented in this step.
  7. Device rule: MPS only if a training step is at least 1.5 times faster than on CPU; otherwise CPU. The outcome is written to `configs/deepfm.yaml` after the speed test.
- **Details the agent fixed where the task left them open** (the user may change them; they are fixed before any result):
  - Bin edges: the quantiles k / 32 (k = 1 … 31) of the non-missing training values, numpy linear interpolation; equal edges are merged; bin = 1 + number of edges ≤ x; missing = bin 0.
  - Standardised input: clip to the [0.1st, 99.9th] training percentiles, then `(x − mean) / std` with the mean and std of the clipped training values; missing: value 0 and indicator 1; field embedding `z · v + m · u`, first-order term `w · z + c · m`.
  - Listwise batches: queries in a new random order every epoch, packed into batches of at most 4,096 rows of whole queries; loss of a query = mean over its positives of `− log softmax`; batch loss = mean over its queries.
  - Initial values: embeddings normal(0, 0.01); first-order weights and bias 0; the MLP with PyTorch's default initialisation.
  - "Range across seeds" = (max − min) / min of the three pooled values, each at the epoch its own curve gives by the epoch rule.
  - Pooled MAP@12 = weighted by queries over V1–V4, as in M7.

## 2026-11-20 M9 step 3: how the memory peak of the standardised path is lowered (recorded before the runs)

- **Where the 11.66 GB came from** (measured with random arrays of the real shapes, no project data): scoring one chunk of 262,144 candidate rows. With the standardised input the field embeddings `e = z · v + m · u` need three tensors of float32 [262144, 63, 16] at once (1.06 GB each), then the joined [262144, 71, 16] tensor and its square for the second-order term: about 6.2 GB for one chunk, against about 3.3 GB with the binned input.
- **What is NOT changed: the scoring chunk.** Scoring the same rows in chunks of another size changes standardised scores by about 1e-7. The cause was measured: the last bits of a matrix product depend on how many rows the call holds (the first-order term `values @ weights`; a `Linear` layer gives other bits for the same row in a call of 1 row, and `Linear(64, 1)` still in a call of 1,000 rows). So `scoring.rows_per_chunk` stays 262,144 and every matrix product still runs once per chunk, on the same input.
- **Change 1 (scoring).** Inside a chunk, the field embeddings and the second-order term are built for `scoring.rows_per_block = 32768` rows at a time and written into one tensor of the full size, which the MLP then reads in one call. These are element-wise operations, look-ups and sums over a row's own fields. New setting in `configs/deepfm.yaml`; it is not part of a configuration id.
- **Change 2 (training rows).** With the standardised input the standardised values are written over the raw values, column by column, instead of into a second float32 [n_rows, 63] array (2.7 GB for a window).
- **Identical outputs.** Tests on small data: the logits are bit-identical for block sizes 1, 7, 50, … for every component variant with code fields and with value fields (`test_deepfm_model.py`, `test_deepfm_train.py`); in-place standardising gives the same bytes (`test_deepfm_inputs.py`); a whole standardised trial (model file, transform, predictions with their scores, per-query metrics) is identical with one pass and with blocks of 7 rows, for both losses (`test_deepfm_trial.py`). With random arrays of the real shapes (3.05 million rows, the real model sizes) the scores are bit-identical and the peak added by scoring falls from 6.2 GB to 2.6 GB (standardised).
- **An added check on the real data, before the runs** (the agent's addition): `scripts/m9_deepfm_rescore.py` loads the saved seed-42 model of the standardised ablation (`08775a5d6efb`, trained and scored before these changes), scores all candidates of V1–V4 again with the new code and compares the Top-12 with the saved predictions, bit for bit. It reads no label and writes nothing. If a single row differs, the extension stops.
- The 255-bin runs use the same scoring code; their encoded inputs are cached as before.
